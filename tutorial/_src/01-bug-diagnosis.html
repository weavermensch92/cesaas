진단 captures-chunks bytea 버그 — 클라이언트와 DB 저장 값의 불일치
probe-bytea.ts 실행 결과 · 1×1 WebP(44 bytes) 송출 → DB SELECT

📤 클라이언트가 보낸 raw bytes SHA256 검증 통과

# probe-bytea.ts 출력
client bytes {
  len: 44,
  hex: '5249464624000000574542505650...c08000',
  hash: '5c37726988a2ad73c4dfae2f4af7d7a1...'
}

# chunks 전송 응답
statuses: [ 200 ]
stored chunk_hash: '5c37726988a2ad...'
# ↑ 서버가 받은 bytes의 hash. 클라이언트와 일치.

💾 DB의 capture_chunks.bytes 실제 저장값 JSON 객체로 깨짐

typeof raw     : string
raw.length    : 664  // 44 bytes인데 664자?
raw[0..40]    : "\\x7b2230223a38322c2231223a37332c..."

# hex 디코드:
\x 7b 22 30 22 3a 38 32 2c 22 31 22 3a 37 33
   {  "  0  "  :  8  2  ,  "  1  "  :  7  3
// → {"0":82,"1":73,... ← JSON 객체 문자열이 통째로 저장됨
⬇
근본 원인
supabase-js v2가 Uint8Array를 INSERT 시 자동으로 PostgreSQL bytea로 변환하지 못하고, JSON.stringify(객체)로 직렬화해버림. 결과적으로 DB에는 실제 이미지 바이트가 아니라 {"0":82,"1":73,...,"43":0} 형태의 객체 문자열이 bytea로 저장됨.

여파: finalize 단계의 합성 hash 검증이 100% 실패 → cluster 생성 0 → normalize 0 → unified lead 0 → Sensor 채널 전체 무용지물. 하지만 chunks 단계는 raw bytes 기준 hash 검증을 먼저 하기 때문에 200을 응답해 클라이언트는 정상 동작인 줄 알았음.
