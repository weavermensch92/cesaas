# T_07.04 — 5 우회 시나리오 (문서화)

> PRD-04 § 6 T-053. 자동 measure 대상이 아닌 **운영 매뉴얼 시나리오**.
> 출장 현장(CTT Moscow 2026) 또는 운영 중 발생 가능. 각 시나리오는 (1) 트리거 (2) 진단 (3) 우회 절차 (4) 사후 검증.

---

## S1 — VPN 시나리오

**트리거**: 러시아 부스 네트워크가 ISP 차단·검열로 Supabase Tokyo 도달 실패.

**진단**:
- Dealer 단말 헤더 `Online` 뱃지가 `Offline`으로 깜빡임 (5초 이상)
- `dealer/index.html`의 IndexedDB 큐 카운트가 증가하지만 drain 안 됨

**우회**:
1. 부스 라우터에서 VPN 활성화 — 권장: Cloudflare WARP (러시아 ToS 검토 후) 또는 Outline
2. VPN 활성 후 단말 새로고침 — Online 복귀 + 큐 자동 drain
3. 큐가 끝까지 안 비면 `localStorage`에서 `hd_dealer_queue` 키 export → 수동 백업

**사후 검증**:
- DB `responses` count 증가 확인
- VPN OFF 후 정상 라우팅으로 복귀 시 정상 동작 확인

---

## S2 — 독립 운영 (Supabase 끊김)

**트리거**: Supabase 전체 region 장애 또는 API 차단 (Tokyo·Sydney 동시).

**진단**:
- Edge Function 호출 모두 5xx
- Admin UI 로그인 실패
- Dealer 단말은 IndexedDB 큐만 쌓임 (응답은 받지만 송출 X)

**우회**:
1. Fly.io fallback 인스턴스로 DNS 전환 (운영 후속 항목 — 현 PoC 미배포)
2. Fly.io 미배포 시: 부스 운영 계속 (응답은 IndexedDB에 안전 저장), Supabase 복구 후 큐 자동 drain
3. 본사 측 보고: `hd_dealer_queue` 백업 → 노트북으로 운반 → Supabase 복구 후 SQL 직접 import

**사후 검증**:
- 복구 후 `responses` 테이블에 누락 없이 전 응답 INSERT 확인
- 동일 idempotency_key는 자동 중복 차단

## S3 — 청크 송출 실패 (Sensor)

**트리거**: Extension이 16KB 청크 송출 8회 재시도 모두 실패 (HMAC 오류·서버 5xx·러시아 ISP 16KB throttle).

**진단**:
- Extension popup의 `lib/error.js` 로그에 8회 재시도 traceback
- 큐가 1000건 한도까지 누적
- `captures` 테이블에 row 없음 (서버 도달 0)

**우회**:
1. **HMAC 키 회전** — R_20 `npm run issue-token` 으로 새 키 발급, Extension config.js 업데이트
2. **청크 크기 축소** — 16KB → 8KB 임시 (코드 변경 + Extension 재빌드)
3. **수동 export** — Extension popup의 "큐 export" → JSON 파일 → 본사 측에서 직접 captures-chunks Edge Function 호출
4. **마지막 수단** — 동영상으로 화면 녹화, 본사가 수동 정규화

**사후 검증**:
- 신규 캡쳐가 finalize까지 성공 (`captures.status='received'`)
- 누적 큐가 비워짐

## S4 — Studio 자연어 빌드 실패

**트리거**: 위버가 Studio에서 자연어 설문 작성 → Claude API 호출 실패 (rate limit·5xx·prompt mismatch).

**진단**:
- `/studio` 페이지에서 "빌드 실패" 메시지
- `llm_calls` 테이블에 status='failed' row + reason 확인

**우회**:
1. **다시 시도** — R_10.06 prompt에 지수 백오프 5회 내장. 일시적 5xx면 자동 회복
2. **수동 YAML 작성** — Studio UI 우회. `C_Common/r_10_rules/` 에 직접 YAML 작성 → `npm run publish-rule -w @hd/r20`로 배포
3. **R_10.06 prompt 정정** — Studio가 의도한 입력 형식과 안 맞으면 위버가 `voice_studio_survey_build` 시스템 프롬프트 정정 → publish-rule → 재시도
4. **기존 설문 복제** — 003_voice.sql의 dealer/visitor 시드 설문을 base로 수동 편집

**사후 검증**:
- `surveys` 테이블에 새 row + survey_questions 정상 INSERT
- 단말에서 새 설문 로드 확인

## S5 — HD 본사 측 요청 시나리오

**트리거**: HD 본사 마케팅팀이 부스 진행 중 "이런 데이터도 추적해줘" 요청 (예: 경쟁사 사용 여부, 구매 검토 시기).

**진단**: 요구사항 자체는 정상 — 신규 데이터 포인트 추가 요청.

**우회 (외부 컨트롤 사이클의 정상 운영)**:
1. 위버가 R_10.09 DataPointToQuestion 호출 → 추가 질문 JSON 생성
2. Studio에서 검토·편집 → 기존 survey에 질문 추가
3. `npm run publish-rule -w @hd/r20 -- --rule R_10.09_DataPointToQuestion --version <new>` (필요 시)
4. 5분 안에 단말이 새 설문 fetch — 부스 진행 중단 없음

**사후 검증**:
- 신규 질문 ID로 `response_answers` row 누적 확인
- HD 본사에 익명 CSV (anon=true) export → 신규 컬럼 확인
