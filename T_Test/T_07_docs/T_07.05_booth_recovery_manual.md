# T_07.05 — 출장 중 부스 즉시 회복 매뉴얼

> PRD-04 § 6 T-054. **CTT Moscow 2026 부스 운영 중 30초 내 대응 가능한 cheat-sheet**.
> 출장 인원이 인터넷 끊긴 상태에서도 읽을 수 있게 — 의도적으로 짧고 명령어 위주.
>
> **연락**: 위버 (그릿지) · 텔레그램 핸들 _운영 시점 등록_

## 0. 첫 30초 — 어디가 문제인지 좁히기

| 증상 | 어디서 보이나 |
|---|---|
| Dealer 단말 헤더 `Offline` | 인터넷·VPN |
| 헤더는 `Online`인데 응답 후 큐 카운트 안 줄어듬 | Supabase API |
| QR 스캔 → "Invalid token" | JWT 만료 또는 revoke |
| `/voice/dealers` 페이지에서 토큰 발급 실패 | Admin 인증 |
| 응답 저장은 되는데 segment가 'other' | R_10.05 룰 |

## 1. Dealer 단말 즉시 조치 (위버 부재 시 부스 인원이 직접)

```text
# 1) 헤더 ? 버튼 → 4쪽 튜토리얼 다시 보기
# 2) 큐 카운트가 0이 안 되면 — 일단 응답 계속 받기
#    (IndexedDB가 1000건까지 저장, 인터넷 복구 시 자동 송출)
# 3) 새 응답 시작 안 되면 — 페이지 새로고침 (F5)
# 4) 그래도 안 되면 — 새 탭에서 같은 URL 다시 열기
#    이전 탭의 큐는 그대로 → 인터넷 복구 시 같이 송출됨
```

위험 신호: 큐 카운트가 500건 넘으면 **즉시 위버 호출** (브라우저 메모리 한계 접근).

## 2. JWT 토큰 즉시 재발급 (Admin 권한 보유 시)

```powershell
# 로컬 r20 CLI 사용 (인터넷 필요)
cd <repo>/R_Runtime/r20
npm run issue-token -w @hd/r20 -- --dealer dealer_001 --event ctt_moscow_2026 --ttl 8
# → 출력의 'url' 필드를 QR로 부스에 표시 (휴대폰 카메라로 스캔)
```

`out/dealer_001-*.png` 자동 생성 — 종이로 출력해 부스 비치 권장 (예비).

## 4. 큐 백업 (Dealer 단말이 회복 불가)

브라우저 DevTools (F12) → Application → IndexedDB → `hd_dealer_queue` → export.

JSON 파일을 USB로 본사 측 (한국) 노트북 이동 → Edge Function 직접 호출:

```bash
# 위버 노트북에서 (인터넷 가능 환경)
for response in $(jq -c '.[]' queue-backup.json); do
  curl -X POST https://<supabase-ref>.supabase.co/functions/v1/responses-receive \
    -H "Authorization: Bearer $DEALER_JWT" \
    -H "Content-Type: application/json" \
    -d "$response"
done
```

같은 idempotency_key면 자동 중복 차단 — 안전.

## 5. R_10.05 segment 매칭 즉시 정정

부스에서 "응답 segment가 자꾸 'other'로 나옴" 보고 시:

```powershell
# 1) 어느 axis 조합이 누락됐는지 진단 — Admin /voice/responses 검색
# 2) 위버 노트북에서 R_10.05 YAML voice_segment 배열 정정
#    (예: agriculture 룰의 axis.usage 값을 'farming'으로도 매칭)
# 3) 즉시 publish:
cd <repo>/R_Runtime/r20
npm run publish-rule -w @hd/r20 -- --rule R_10.05_Classification --version 2026-05-XX.NNN
# 4) responses-receive는 5분 캐시 안 자동 반영
# 5) 영향받는 기존 응답 재산출은 별도:
npm run retrigger -w @hd/r20 -- --cluster-ids <id1>,<id2> --priority high
```

`shared/segments.ts`의 inline fallback은 DB 로드 실패 시만 발동 — 정상 운영 중에는 publish-rule이 즉시 작동.

## 6. 점수가 갑자기 0 또는 NULL — scoring 끊김

부스에 표시되는 lead.score / priority가 안 보이면 (관리자 화면 기준):

```sql
-- Supabase SQL Editor에서
SELECT id, version, status, created_at FROM rule_versions
 WHERE rule_id IN ('R_10.01_LeadScoring', 'R_10.02_LeadQuality', 'R_10.05_Classification')
 ORDER BY rule_id, created_at DESC LIMIT 9;
-- 각 rule에 status='active' row 1개씩 있어야 정상.
-- 없으면 — 020_seed_r10_01_02.sql 또는 019_seed_r10_05_classification.sql 마이그레이션 누락.
```

긴급 복구:
```bash
# 위버 노트북에서
cd <repo>/R_Runtime/r20
npm run publish-rule -w @hd/r20 -- --rule R_10.01_LeadScoring  # version 필드 자동
npm run publish-rule -w @hd/r20 -- --rule R_10.02_LeadQuality
npm run publish-rule -w @hd/r20 -- --rule R_10.05_Classification
```

## 7. 마지막 수단 — 완전 우회

부스 인터넷·노트북 모두 실패 시:

1. Dealer 단말의 IndexedDB만 유지 → 응답 받기 계속 (오프라인 큐)
2. 종이 노트로 회사명·연락처 backup 기록
3. 본사 복귀 후 (한국) 큐 + 종이 backup 비교 → 누락분만 수동 import
4. 출장 종료 후 24h 이내 위버에게 보고

부스 마비 자체보다 **데이터 누락이 큰 손실** — 받는 것만이라도 어떻게든 받기.
